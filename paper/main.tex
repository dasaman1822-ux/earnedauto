\begin{abstract}
Automated remediation can reduce the time required to recover from infrastructure
failures, but unrestricted automation can also execute harmful actions when the
correct remediation is uncertain. This project presents Earned Autonomy, a trust
gate positioned between failure detection and remediation execution. The gate
determines whether a candidate remediation should be automatically executed,
proposed for human approval, or escalated to a human operator. The decision is
based on three factors: action reversibility, blast radius, and accumulated
evidence of successful outcomes. Evidence is represented using a Beta posterior,
with a conservative lower posterior percentile used instead of the posterior
mean. This design allows autonomy to be earned through repeated successful
outcomes while retaining safety constraints for actions with larger blast
radius or lower reversibility. A public Blue Gene/L (BGL) system log dataset is
used to derive the shape of incident distributions, while a controlled
simulator is used for reproducible experimentation and later benchmarking.
The current implementation establishes the incident simulator, configurable
action and threshold definitions, Bayesian evidence tracking, the trust-gate
decision logic, and safety tests. Further evaluation will compare the gate with
always-ask and always-act baselines using automatic resolution rate, mean time
to recovery, human interruptions, and unsafe automatic executions.
\end{abstract}

\section{Introduction}

Modern infrastructure systems increasingly use automation to detect failures
and initiate remediation actions. Automation can reduce recovery time and
decrease the operational workload placed on human engineers. However, an
automation system that executes every proposed action without considering
context can also turn an uncertain diagnosis into an unsafe infrastructure
change.

The central problem addressed by this project is therefore not failure
detection itself, but the decision of whether an already proposed remediation
action has earned sufficient trust to execute automatically.

Earned Autonomy introduces a decision layer between a failure detector and an
action executor. Instead of treating automation as a binary property, the
system provides three possible decisions: \textit{AUTO}, \textit{PROPOSE}, and
\textit{ESCALATE}. An action can initially require human involvement and later
become eligible for automatic execution as successful evidence accumulates.

The design is intentionally based on three factors. Reversibility represents
how easily an action can be undone. Blast radius represents the potential
scope of impact if an action is incorrect. Accumulated evidence represents
historical observations of whether a particular action has successfully
resolved incidents in a particular machine-class context.

The project prioritizes limiting unsafe automatic executions rather than
maximizing the number of actions executed automatically. The final evaluation
will determine whether this approach provides useful automation while
maintaining this safety objective.

\section{Problem Statement}

A conventional automated remediation workflow can be represented as:

\begin{equation}
\text{Failure Detection}
\rightarrow
\text{Candidate Action}
\rightarrow
\text{Action Execution}
\end{equation}

The missing component is a trust decision between the candidate action and its
execution.

An action that is appropriate in one context may not be appropriate in
another. For example, restarting a stateless service may have a relatively
small and reversible impact, whereas reclaiming disk space by deleting
temporary files can have a larger consequence if the action is applied
incorrectly.

Earned Autonomy therefore treats the remediation decision as a function of
action properties, environmental risk, and observed historical evidence.

\section{Project Scope}

The project implements a Python-based trust gate for automated infrastructure
remediation.

The gate is responsible for:

\begin{itemize}
    \item evaluating candidate remediation actions;
    \item combining reversibility, blast radius, and evidence;
    \item maintaining evidence separately for action type and machine class;
    \item producing AUTO, PROPOSE, or ESCALATE decisions;
    \item providing configurable decision thresholds; and
    \item supporting reproducible simulation and benchmarking.
\end{itemize}

The project does not implement a failure detector, infrastructure executor,
monitoring dashboard, or machine-learning failure prediction model.

The simulator is used to provide reproducible incidents and, in later stages,
ground truth for determining whether an action was safe or successful.

\section{Earned Autonomy Trust Gate}

\subsection{Design Overview}

The trust gate combines three factors:

\begin{enumerate}
    \item reversibility;
    \item blast radius; and
    \item accumulated evidence.
\end{enumerate}

The resulting decision is one of:

\begin{itemize}
    \item \textbf{AUTO}: the action may be executed automatically;
    \item \textbf{PROPOSE}: the action may be proposed to a human operator; or
    \item \textbf{ESCALATE}: human intervention is required.
\end{itemize}

\subsection{Bayesian Evidence}

Evidence for an action is represented using a Beta posterior.

The initial prior is:

\begin{equation}
Beta(1,1)
\end{equation}

A successful outcome increments $\alpha$, while a failed outcome increments
$\beta$:

\begin{equation}
\alpha' = \alpha + 1
\end{equation}

\begin{equation}
\beta' = \beta + 1
\end{equation}

Evidence is maintained separately for each combination of action type and
machine class. This prevents successful outcomes for one context from being
treated as evidence for every other context.

Rather than using the posterior mean as the evidence score, the gate uses a
conservative lower posterior percentile:

\begin{equation}
E_L = Beta^{-1}(0.05;\alpha,\beta)
\end{equation}

where $E_L$ represents the lower evidence bound used by the trust calculation.

The implementation uses SciPy's Beta distribution percent-point function to
calculate this value directly.

\subsection{Trust and Risk}

The trust score is calculated as:

\begin{equation}
Trust = Reversibility \times E_L
\end{equation}

The normalized blast radius is used as the risk score:

\begin{equation}
Risk = BlastRadius
\end{equation}

The decision rule is:

\begin{equation}
\text{AUTO}
\quad\text{if}\quad
Trust > T_A
\land
Risk < R_C
\land
History = True
\end{equation}

Otherwise:

\begin{equation}
\text{PROPOSE}
\quad\text{if}\quad
Trust > T_P
\end{equation}

and:

\begin{equation}
\text{ESCALATE}
\quad\text{otherwise}
\end{equation}

where $T_A$ is the automatic-execution threshold, $T_P$ is the proposal
threshold, and $R_C$ is the risk ceiling.

\section{Implementation}

The trust gate is implemented as a small Python component.

The primary implementation is divided into two modules. The evidence module
contains the Beta evidence model and evidence store. The gate module loads
configuration, validates the configured factors and thresholds, calculates
trust and risk, and returns a structured gate result.

The action configuration is stored in YAML so that action properties can be
changed without modifying the gate implementation.

Similarly, the decision thresholds are stored separately from the gate logic.

This separation allows the implementation to remain small and makes the
configuration explicit and reproducible.

\section{Week 2 Verification}

The Week 2 implementation includes safety tests for the trust gate.

The first safety condition is that an action with no observed history must
never receive an AUTO decision. This prevents the system from treating the
initial Beta prior as sufficient evidence for automatic execution.

The second condition is that an action with a high blast radius must not
receive an AUTO decision, even after accumulating successful outcomes.

Additional tests verify that the gate can produce all three relevant
decisions under appropriate conditions.

The automated test suite currently reports:

\begin{equation}
5\ tests\ passed
\end{equation}

The Week 2 implementation was also connected to the 1,000-incident simulator
for an end-to-end check.

\section{Project Progress}

During Week 1, the repository and project structure were established, the BGL
dataset was analyzed, the incident and action data structures were defined,
and the simulator was implemented. The simulator was used to generate 1,000
incidents and produce a distribution plot.

During Week 2, the three trust factors were implemented, Beta evidence tracking
was added, action and threshold configuration was externalized to YAML, and

The implementation was verified using automated tests and a 1,000-incident
end-to-end check.

\section{Next Stage}

The next stage of the project will introduce outcome modeling into the
simulator. The simulator must distinguish between actions that correctly
resolve an incident, actions that appear to work but fail to address the
underlying problem, and actions that cause harmful outcomes.

This outcome model will provide the ground truth required for the evidence
store to learn from remediation results.

The resulting system will then be used to demonstrate how an action can move
from ESCALATE to PROPOSE and eventually to AUTO as successful evidence
accumulates.

The project will subsequently compare Earned Autonomy with baseline strategies
including always-ask and always-act.

The planned evaluation metrics are:

\begin{itemize}
    \item automatic resolution rate;
    \item mean time to recovery;
    \item human interruptions; and
    \item unsafe automatic executions.
\end{itemize}

A threshold sweep will also be performed to examine the relationship between
automation and safety.

\section{Conclusion}

Earned Autonomy provides a trust-gating approach for automated infrastructure
remediation. Instead of assuming that a remediation action is always safe or
always requires human approval, the system evaluates whether the action has
earned the right to execute automatically.

The current implementation establishes the core mechanism using reversibility,
blast radius, and conservative Bayesian evidence. It also establishes a
reproducible simulator and safety tests for the first version of the gate.

The remaining evaluation will determine how this design performs against
simple automation baselines and whether accumulated evidence can increase
useful autonomy without producing an unacceptable number of unsafe automatic
executions.
